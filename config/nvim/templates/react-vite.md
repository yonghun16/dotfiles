# AI/Human 작업 경계 규칙
AI(Claude)는 **폴더 위치가 아니라 파일 상단의 `@owner` 태그**로 작업 가능
여부를 판단합니다. `components/`든 `stores/`든 위치와 무관하게, 태그
하나로 전부 결정됩니다. **파일마다 "이건 누가 해야 하나"를 새로 판단하지
마세요.** 아래 규칙대로 태그를 확인하고 따르면 됩니다.

## 태그 상태
| 태그 | 의미 | AI 작업 가능 여부 |
|---|---|---|
| `// @owner: ai` | AI가 만들었거나 아직 작업 중인 파일 | ✅ 자유롭게 작업 |
| `// @owner: human` | Human이 소유권을 넘겨받은 파일 | ❌ 금지 — 읽기만, 수정/생성 금지 |
| (태그 없음) | 이 규칙 도입 이전의 기존 코드 등, 미지정 상태 | ❌ 기본값은 Human으로 간주 — 먼저 확인 |

## 기본 원칙
1. **새로 만드는 모든 파일**(폴더 위치 무관)에는 AI가 파일 최상단에
   `// @owner: ai`를 답니다.
   ~~~ts
   // @owner: ai
   ~~~
2. `@owner: ai` 태그가 붙어 있는 동안에는 AI가 해당 파일을 계속
   수정/보완할 수 있습니다.
3. Human이 파일을 검토했거나 직접 손을 대기 시작하면, 태그를
   `// @owner: human`으로 바꿉니다. **태그가 바뀐 순간부터 AI는 그 파일을
   다시 수정하지 않고 읽기만 합니다.**
4. Human이 다시 AI에게 맡기고 싶으면 태그를 `// @owner: ai`로 되돌립니다.
   그때부터 다시 AI가 자유롭게 작업할 수 있습니다.
5. 태그가 아예 없는 파일(이 규칙을 도입하기 전에 작성된 기존 코드 등)은
   **기본값을 Human으로 간주**합니다. 안전을 위해 AI는 먼저 건드리지 않고,
   작업이 필요하면 태그를 붙여도 되는지 먼저 확인합니다.

## 파일 단위이지 폴더 단위가 아닙니다
같은 `stores/`나 `hooks/` 폴더 안에서도 파일별로 태그가 다를 수 있습니다.
`@owner: ai`가 붙은 store 파일은 AI가 자유롭게 작업하고, `@owner: human`이
붙은 component 파일은 AI가 건드리지 않습니다. 폴더 이름으로 담당을
추측하지 말고 **항상 파일 상단의 태그를 확인**하세요.

## 검토를 요청해야 하는 경우 (권장)
`@owner: ai`로 작업 중이더라도, 아래에 해당하면 코드를 계속 넓혀가기보다
먼저 Human에게 검토를 요청하고 태그를 `@owner: human`으로 넘길지 물어보는
것을 권장합니다 (강제 규칙은 아니며, 놓치기 쉬운 위험 신호에 가깝습니다).
특히 `stores/`, 인증·결제·권한 관련 로직, 도메인 규칙이 들어간 `hooks/`나
`utils/`에서 자주 해당됩니다.
1. 틀리면 신뢰도/안전/데이터 무결성에 영향이 가는가?
2. 임계값·정책·규칙 같은 도메인 지식이 필요한가?
3. 잘못됐을 때 되돌리기 어렵거나 비용이 큰가?

반대로 아래에 해당하면 검토 없이 계속 작업해도 괜찮은 신호입니다.
4. 명세만 있으면 패턴대로 반복 구현 가능한가?
5. 테스트로 결과를 촘촘히 검증할 수 있는가?

## `@owner: human` 파일에 변경이 필요할 때
`@owner: human`이 붙은 파일을 참조해야 하는 기능을 만들 때는:
1. 그 파일의 기존 함수/타입을 **그대로 호출**해서 쓰세요 (수정 금지).
2. 새 함수나 수정이 필요하다고 판단되면, **코드를 직접 만들지 말고**
   무엇이 왜 필요한지 먼저 설명하세요. Human이 판단 후 작성하거나, 태그를
   다시 `@owner: ai`로 풀어줍니다.

## 요약
- **태그가 전부입니다**: `@owner: ai` = AI 자유 작업, `@owner: human` = AI
  금지(읽기만), 태그 없음 = 기본값 Human으로 간주
- 새로 만드는 파일은 폴더 위치와 무관하게 전부 `@owner: ai`로 시작
- Human이 넘겨받으면 태그를 `@owner: human`으로 바꿔서 잠그고, 다시
  맡기려면 `@owner: ai`로 되돌림
- 도메인 판단이 필요한 코드는 계속 작업하기보다 먼저 검토를 요청하는 것을
  권장
- 이 규칙은 "src 구조 원칙"(코드를 어디에 둘지)과는 독립적입니다 — 위치는
  구조 원칙이, 담당은 `@owner` 태그가 정합니다.
- 애매하면 판단하지 말고 먼저 물어볼 것

# src 구조 원칙 (범용 구조)
이 프로젝트의 `src/` 구조는 **프로젝트 규모나 도메인과 무관하게 항상 동일한
모양을 유지하는 범용 구조**입니다. 어떤 프로젝트를 하더라도 최상위 폴더
구성(`app/ assets/ components/ config/ features/ hooks/ lib/ stores/ types/
utils/`)은 바뀌지 않는다는 전제로 작업합니다. 이렇게 하는 이유는, 코드는
AI가 작성하고 사람은 리뷰만 하는 워크플로우에서 **사람이 항상 예측 가능한
위치에서 코드를 찾을 수 있어야 하기 때문**입니다.

새 파일을 어디에 둘지 판단하는 기준은 단 하나입니다.
> **이 코드를 2개 이상의 feature가 같이 쓰는가?**
> - 예 → 최상위 공용 폴더(`components/`, `hooks/`, `utils/`, `types/`, `lib/`, `stores/`)
> - 아니오(하나의 기능에서만 쓰임) → `features/<해당 기능>/` 안에

이 질문 하나로 판단이 애매해지지 않도록, 폴더를 늘리거나 이름을 바꾸기 전에
반드시 위 기준으로 먼저 판단합니다. 프로젝트마다 새로운 최상위 폴더를 만들지
않습니다.

이 섹션은 **코드를 어디에 둘지**에 대한 기준이고, **누가 그 파일을 수정할
수 있는지**는 위 "AI/Human 작업 경계 규칙"의 `@owner` 태그가 별도로
결정합니다. 두 규칙은 서로 독립적입니다.

# TypeScript 규칙
- JavaScript보다 TypeScript 사용을 우선합니다.
- `any` 사용을 피합니다.
- 명확한 타입 정의를 작성합니다.
- 객체 구조와 컴포넌트 Props는 interface 사용을 우선합니다.
- 여러 feature에서 공용으로 쓰는 타입은 `src/types/`에 둡니다. 하나의 feature
  안에서만 쓰는 타입은 해당 `features/<feature-name>/types/`에 둡니다.
- 여러 feature가 공유하는 외부 계약(API/소켓 payload 등)의 타입은
  `src/types/`에 정의하고, 클라이언트/서버 양쪽에서 동일한 이름 규칙을
  사용합니다.
- 타입 파일도 새로 만들 때는 `@owner: ai`를 달고, 이미 `@owner: human`인
  타입 파일은 직접 수정하지 말고 필요성을 먼저 설명하세요.

좋은 예:
~~~ts
interface User {
  id: string;
  name: string;
}
~~~

피해야 할 예:
~~~ts
const user: any = {};
~~~

}

# 프로젝트 문서 관리 (Obsidian / Quartz)
코드 외의 프로젝트 문서(기획, 구현 프롬프트, 개발 프로세스, 회의/결정 기록 등)는
`docs/content/`(Obsidian Vault, Quartz 5로 사이트 빌드)에서 관리되는 마크다운
파일로 작성합니다. `docs/` 폴더에는 Quartz 5 관련 설정/코드가 함께 있으므로,
Vault(문서)는 반드시 `docs/content/` 하위에만 작성하고 `docs/` 바로 아래(Quartz
설정 파일들이 있는 위치)에는 문서를 두지 않습니다. 이 문서들은 `src/` 하위의
코드 문서화(TSDoc)와는 별개입니다.

**문서 작성 방식(폴더 구조, frontmatter, 태그, MOC 링크, 문서 최신성 관리
등)은 `docs/CLAUDE.md`에서 관리합니다.** `docs/` 하위에서 작업할 때는 이
파일과 `docs/CLAUDE.md`가 함께 적용되므로, 문서 관련 세부 규칙은 여기서
반복하지 않고 그쪽을 따릅니다. 이 파일(루트)에는 "문서는 `docs/content/`
안에만 두고 `docs/` 최상위(Quartz 설정 위치)에는 두지 않는다"는 경계만
유지합니다.

# React 규칙
## 컴포넌트
- Functional Component를 사용합니다.
- Props는 TypeScript 타입을 정의합니다.
- 하나의 컴포넌트는 하나의 책임만 가지도록 합니다.
- 너무 큰 컴포넌트는 작은 컴포넌트로 분리합니다.
- 불필요한 상태 관리를 만들지 않습니다.
- 여러 feature가 같이 쓰는 컴포넌트만 `src/components/`에 둡니다. 하나의
  feature에서만 쓰는 컴포넌트는 `features/<feature-name>/components/`에 둡니다.
- 새로 만드는 컴포넌트 파일에는 `@owner: ai`를 답니다. `@owner: human`인
  기존 컴포넌트는 수정하지 않습니다.

## Hook
- 반복되는 로직은 Custom Hook으로 분리합니다.
- 하나의 Hook은 하나의 역할만 담당합니다.
- 컴포넌트 내부에 큰 비즈니스 로직을 작성하지 않습니다.
- 여러 feature가 공유하는 Hook은 `src/hooks/`에 둡니다. 특정 feature 전용
  Hook은 `features/<feature-name>/hooks/`에 둡니다.
- 도메인 판단이 들어간 Hook(예: 권한 체크, 요금제 로직)은 작성 후 "검토를
  요청해야 하는 경우" 기준에 따라 Human 검토를 먼저 요청하는 것을
  권장합니다.

이름 규칙:
~~~
useAuth.ts
usePosts.ts
~~~

# 프로젝트 구조
다음 구조를 유지합니다. **이 구조는 프로젝트 규모/도메인과 무관하게 고정입니다.**
최상위 폴더를 새로 만들지 않고, 새 코드는 항상 이 중 하나에 배치합니다.
`features/` 하위의 실제 폴더 이름([[bingo-room 등]])만 프로젝트마다 달라집니다.
아래 트리는 배치 기준이며, 각 파일의 실제 작업 가능 여부는 폴더가 아니라
`@owner` 태그로 결정됩니다.

~~~

**폴더별 한 줄 설명**

| 폴더 | 기준 |
|---|---|
| `app/` | 라우팅과 전역 Provider를 "조립"만 하는 곳. 비즈니스 로직 없음 |
| `assets/` | 이미지/폰트 등 정적 파일 |
| `components/` | 2개 이상 feature가 같이 쓰는 UI 컴포넌트만 |
| `config/` | 환경변수, 전역 상수 |
| `features/` | 실제 기능 로직. 대부분의 신규 코드는 여기 하위에 생김 |
| `hooks/` | 2개 이상 feature가 같이 쓰는 Hook만 |
| `lib/` | 외부 라이브러리를 초기화/래핑한 인스턴스 |
| `stores/` | 앱 전체가 공유하는 전역 상태만 |
| `types/` | 2개 이상 feature가 공유하는 타입만 |
| `utils/` | 외부 의존성 없는 순수 함수만 |

담당(AI/Human)은 이 표가 아니라 각 파일 상단의 `@owner` 태그로 결정됩니다
("AI/Human 작업 경계 규칙" 참고).

상황에 맞는 도구를 사용합니다.

로컬 상태:

useReducer
~~~

전역 상태:
~~~

서버 상태:
~~~
React Query

- 하나의 feature 안에서만 쓰는 상태는 `features/<feature-name>/stores/`에,
  2개 이상 feature가 공유하는 상태만 `src/stores/`에 둡니다.
- (실시간/서버 동기화 원칙 적용 여부는 최상단 "프로젝트 설정 > 실시간/서버
  동기화 원칙" 참고. 해당하는 프로젝트라면 상태의 원본 소스는 항상
  서버이며, 클라이언트는 서버에서 받은 상태를 그대로 반영합니다.)
- store 파일도 새로 만들 때는 `@owner: ai`를 달고 작성하되, 정책/임계값
  같은 도메인 판단이 들어가면 "검토를 요청해야 하는 경우" 기준에 따라
  Human 검토를 먼저 요청하는 것을 권장합니다. 이미 `@owner: human`인
  store는 그대로 호출만 하고 수정이 필요하면 먼저 설명하고 요청합니다.
- 새로운 상태 관리 라이브러리를 추가하기 전에 이유를 설명합니다.

# 통신 규칙
최상단 "프로젝트 설정 > 통신 방식"에서 고른 방식에 맞게 아래 예시를 이
섹션 전체에 걸쳐 다시 작성하세요. 지금은 Socket.io 기준 예시가 채워져
있습니다.

예시(Socket.io 기반 실시간 통신인 경우):
- 소켓 이벤트 이름은 `snake_case`로 통일합니다.
- 소켓 클라이언트 인스턴스는 `src/lib/socket.ts`에서 단일 인스턴스로 관리하고,
  여러 곳에서 개별적으로 `io()`를 호출하지 않습니다.
- 특정 feature의 emit/on 로직은 각 `features/<feature-name>/api/`에서
  `lib/socket.ts`의 인스턴스를 가져다 씁니다.
- 연결 해제/재연결 상황을 항상 고려합니다.
- 여러 feature가 공유하는 이벤트 payload 타입은 `src/types/`에 정의한 뒤
  사용합니다.

# 에러 처리 규칙
- 에러는 명확하게 처리합니다.
- 빈 catch 문을 사용하지 않습니다.
- 사용자에게 의미 있는 에러 메시지를 제공합니다.

피해야 할 예:
~~~ts
try {
} catch {}
~~~

권장:
~~~ts
try {
} catch (error) {
  console.error("Failed:", error);
}
~~~

- 관련 없는 변경을 섞지 않습니다.

# AI 작업 규칙
AI는 다음을 지킵니다.
1. **코드를 만들기 전에 대상 파일 상단의 `@owner` 태그를 확인합니다.**
   `@owner: human`이거나 태그가 아예 없으면(기본값 Human) 코드를 작성하지
   않고 필요한 변경사항을 설명만 합니다. `@owner: ai`이거나 새로 만드는
   파일이면 자유롭게 작업하고, 새 파일에는 반드시 `// @owner: ai`를
   답니다.
2. 코드를 수정하기 전에 기존 구현을 확인합니다.
3. 변경 이유를 설명합니다.
4. 새 파일 생성 시 전체 코드를 제공합니다.
5. 영향 범위를 알려줍니다.
6. 큰 구조 변경은 먼저 사용자에게 확인합니다.
7. 새 파일을 만들 때는 항상 "2개 이상 feature 공용인가, feature 전용인가"를
   먼저 판단하고 그에 맞는 위치(`src 구조 원칙` 섹션 참고)에 배치한 뒤,
   `@owner: ai` 태그를 달아 만듭니다. 새로운 최상위 폴더를 임의로 만들지
   않습니다.
8. 도메인 판단(임계값, 정책, 신뢰도/안전/데이터 무결성에 영향)이 필요하다고
   느껴지면, `@owner: ai` 상태여도 계속 밀어붙이지 않고 먼저 Human에게
   검토를 요청합니다.
9. 새로운 기능에 대한 구현 프롬프트나 개발 프로세스를 작성/수정할 때는
   `docs/content/` 폴더(Obsidian Vault)의 알맞은 주제별 폴더(`기획/`, `개발/` 등)에
   저장합니다. `docs/content/` 바로 아래에 파일을 흩어놓지 않고, `docs/` 최상위
   (Quartz 설정 위치)에는 절대 문서를 두지 않습니다. 세부 작성 규칙(frontmatter,
   태그, MOC 링크, 최신성 관리 등)은 `docs/CLAUDE.md`를 따릅니다.

# 개발 선호 사항
선호:
- 깔끔한 TypeScript 코드
- Functional React Component
- TSDoc 문서화
- Tailwind CSS
- 재사용 가능한 컴포넌트
- 명확한 관심사 분리
- `@owner` 태그를 존중하고, 애매하면 먼저 물어보는 태도

피하기:
- 불필요한 추상화
- 과도한 의존성 추가
- 너무 큰 컴포넌트
- `any` 사용
- 이유 없는 구조 변경
- 새로운 최상위 폴더 추가 (`src 구조 원칙` 위반)
- `@owner: human` 파일이나 태그 없는 기존 파일을 임의로 수정하는 것
- 새 파일을 만들면서 `@owner: ai` 태그를 빠뜨리는 것
