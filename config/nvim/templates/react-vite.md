# src 구조 원칙 (범용 구조)

이 프로젝트의 `src/` 구조는 **프로젝트 규모나 도메인과 무관하게 항상 동일한
모양을 유지하는 범용 구조**입니다. 어떤 프로젝트를 하더라도 최상위 폴더
구성(`app/ assets/ components/ config/ features/ hooks/ lib/ stores/ types/
utils/`)은 바뀌지 않는다는 전제로 작업합니다. 이렇게 하는 이유는, 코드는
AI가 작성하고 사람은 리뷰만 하는 워크플로우에서 **사람이 항상 예측 가능한
위치에서 코드를 찾을 수 있어야 하기 때문**입니다.

새 파일을 어디에 둘지 판단하는 기준은 단 하나입니다.

> **이 코드를 2개 이상의 feature가 같이 쓰는가?**
> - 예 → 최상위 공용 폴더(`components/`, `hooks/`, `utils/`, `types/`, `lib/`, `stores/`)
> - 아니오(하나의 기능에서만 쓰임) → `features/<해당 기능>/` 안에

이 질문 하나로 판단이 애매해지지 않도록, 폴더를 늘리거나 이름을 바꾸기 전에
반드시 위 기준으로 먼저 판단합니다. 프로젝트마다 새로운 최상위 폴더를 만들지
않습니다.


# TypeScript 규칙

- JavaScript보다 TypeScript 사용을 우선합니다.
- `any` 사용을 피합니다.
- 명확한 타입 정의를 작성합니다.
- 객체 구조와 컴포넌트 Props는 interface 사용을 우선합니다.
- 여러 feature에서 공용으로 쓰는 타입은 `src/types/`에 둡니다. 하나의 feature
  안에서만 쓰는 타입은 해당 `features/<feature-name>/types/`에 둡니다.
- 여러 feature가 공유하는 외부 계약(API/소켓 payload 등)의 타입은
  `src/types/`에 정의하고, 클라이언트/서버 양쪽에서 동일한 이름 규칙을
  사용합니다.

좋은 예:

~~~ts
interface User {
  id: string;
  name: string;
}
~~~

피해야 할 예:

~~~ts
const user: any = {};
~~~

# 프로젝트 문서 관리 (Obsidian / Quartz)

코드 외의 프로젝트 문서(기획, 구현 프롬프트, 개발 프로세스, 회의/결정 기록 등)는
`docs/content/`(Obsidian Vault, Quartz 5로 사이트 빌드)에서 관리되는 마크다운
파일로 작성합니다. `docs/` 폴더에는 Quartz 5 관련 설정/코드가 함께 있으므로,
Vault(문서)는 반드시 `docs/content/` 하위에만 작성하고 `docs/` 바로 아래(Quartz
설정 파일들이 있는 위치)에는 문서를 두지 않습니다. 이 문서들은 `src/` 하위의
코드 문서화(TSDoc)와는 별개입니다.

## 폴더 구조

- **folder-page가 켜져 있으므로 폴더 자체가 목록 페이지가 됩니다.** 문서를
  `docs/content/` 바로 아래에 평평하게 흩어놓지 말고, 반드시 주제별 폴더로
  묶어서 넣습니다.
  - `기획/` — 요구사항, 기능 정의 등 기획 문서
  - `개발/` — 개발 프로세스, 구현 프롬프트 등 개발 관련 문서
  - `private/` — 초안/메모용. `ignorePatterns`에 이미 제외되어 있어 퍼블리시되지
    않습니다. 아직 정리되지 않은 초안은 우선 여기에 둡니다.
  - [[프로젝트 성격에 따라 필요한 주제별 폴더를 추가 (예: `운영/`, `회의록/`)]]
  - 새로운 주제가 생기면 임의로 루트에 파일을 만들지 말고, 어울리는 폴더가 없는지
    먼저 확인하고 필요하면 새 폴더를 제안합니다.
- 파일명: 한글 파일명을 허용합니다 (예: `개발프로세스.md`).
  코드 파일명 규칙(PascalCase/camelCase)과는 별도의 규칙입니다.

## 폴더 vs 태그

- **폴더**는 큰 카테고리(기획/개발/회의록) 분류에만 사용합니다.
- **태그**는 폴더를 가로지르는 속성에 사용합니다 (예: `#스펙`, `#체크리스트`,
  `#진행중`). tag-page가 켜져 있어 태그를 붙이면 자동으로 태그별 모음 페이지가
  생성되므로, "이 문서는 어떤 성격인가"를 나타낼 때는 폴더를 새로 만들기보다
  태그를 답니다.

## MOC(허브) 패턴

- `docs/content/index.md`는 하위 문서들을 `[[문서명]]` 형태로 모아 링크하는
  허브(MOC) 역할을 합니다. 새 문서를 추가하면 관련된 허브 문서(`index.md` 또는
  하위 폴더의 허브 문서)에서 반드시 링크를 걸어줍니다.
- graph/backlinks 플러그인이 켜져 있어 링크를 많이 걸수록 그래프 뷰와 백링크
  패널이 쓸모 있어집니다. **링크 없이 고립된 문서를 만들지 않습니다** — 새
  문서를 만들면 최소 하나 이상의 다른 문서(허브 문서 또는 관련 문서)에서
  링크로 연결되어 있는지 확인합니다.
- 문서 간 연관이 있으면 본문 중간에도 `[[관련 문서명]]` 링크를 적극적으로
  겁니다.

## 옵시디언 전용 파일

- `docs/content/.obsidian/`, `docs/content/templates/`는 이미 `ignorePatterns`로
  빌드에서 제외되어 사이트에 노출되지 않습니다. 옵시디언 설정이나 문서 템플릿은
  그대로 저장소에 둬도 됩니다 (별도로 `.gitignore` 처리하거나 삭제할 필요 없음).

## 문서 종류 예시

- **구현 프롬프트 문서** (`개발/`): 특정 기능을 AI 코딩 툴에 맡길 때 사용한/사용할
  프롬프트 원문을 그대로 보관합니다. 나중에 같은 기능을 다시 만들거나 다른
  프로젝트에 재사용할 때 참고합니다.
- **개발 프로세스 문서** (`개발/`): 단계별 개발 순서, 완료 기준, 체크리스트 등을
  기록합니다.
- **기획 문서** (`기획/`): 요구사항, 흐름, 기능 정의 등을 기록합니다.
- **초안/메모** (`private/`): 아직 정리되지 않았거나 외부에 공개하고 싶지 않은
  내용.

AI가 새로운 프롬프트 문서나 프로세스 문서를 작성/수정할 때도 위 폴더 구조,
태그 사용법, MOC 링크 규칙을 따릅니다.


# React 규칙

## 컴포넌트

- Functional Component를 사용합니다.
- Props는 TypeScript 타입을 정의합니다.
- 하나의 컴포넌트는 하나의 책임만 가지도록 합니다.
- 너무 큰 컴포넌트는 작은 컴포넌트로 분리합니다.

- 여러 feature가 같이 쓰는 컴포넌트만 `src/components/`에 둡니다. 하나의

## Hook

- 반복되는 로직은 Custom Hook으로 분리합니다.
- 하나의 Hook은 하나의 역할만 담당합니다.
- 컴포넌트 내부에 큰 비즈니스 로직을 작성하지 않습니다.
- 여러 feature가 공유하는 Hook은 `src/hooks/`에 둡니다. 특정 feature 전용
  Hook은 `features/<feature-name>/hooks/`에 둡니다.

이름 규칙:

~~~
useAuth.ts
usePosts.ts
~~~


# 프로젝트 구조

다음 구조를 유지합니다. **이 구조는 프로젝트 규모/도메인과 무관하게 고정입니다.**
최상위 폴더를 새로 만들지 않고, 새 코드는 항상 이 중 하나에 배치합니다.
`features/` 하위의 실제 폴더 이름([[bingo-room 등]])만 프로젝트마다 달라집니다.

~~~
project-root/
├── docs/                     # Quartz 5 관련 코드/설정
│   └── content/                # Obsidian Vault (문서 사이트)
│       ├── index.md
│       ├── 기획/
│       ├── 개발/
│       ├── private/
│       ├── .obsidian/
│       └── templates/
└── src/
    ├── app/                   # 앱의 "조립부" — 라우팅 + 전역 Provider + 진입점
    │   ├── routes/              # URL 단위 화면. 여러 feature를 조합해 실제 페이지를 구성
    │   ├── App.tsx                # 루트 컴포넌트 (Provider 조합)
    │   ├── Router.tsx              # 라우트 정의
    │   └── Providers.tsx            # 전역 Provider 묶음
    │
    ├── assets/                 # 이미지, 폰트 등 정적 파일
    │
    ├── components/              # 2개 이상 feature가 같이 쓰는 범용 UI 컴포넌트
    │   ├── ui/                    # 버튼, 인풋 등 원자 단위
    │   └── layout/                  # 헤더, 사이드바 등 화면 뼈대
    │
    ├── config/                   # 환경변수, 전역 설정/상수
    │
    ├── features/                  # 실제 비즈니스 로직 대부분이 위치하는 곳 (도메인 단위)
    │   └── [[feature-name]]/        # 프로젝트마다 실제 도메인에 맞게 이름 결정
    │       ├── api/                   # 이 feature 전용 서버 통신
    │       ├── components/
    │       ├── hooks/
    │       ├── stores/
    │       ├── types/
    │       └── utils/
    │
    ├── hooks/                     # 2개 이상 feature가 같이 쓰는 범용 Hook
    │
    ├── lib/                        # 외부 라이브러리 인스턴스/초기화 (axios, socket 등)
    │
    ├── stores/                      # 앱 전체가 공유하는 전역 상태
    │
    ├── types/                        # 프로젝트 전역 공통 타입
    │
    └── utils/                         # 순수 헬퍼 함수 (외부 의존성 없음)
~~~

**폴더별 한 줄 설명**

| 폴더 | 기준 |
|---|---|
| `app/` | 라우팅과 전역 Provider를 "조립"만 하는 곳. 비즈니스 로직 없음 |
| `assets/` | 이미지/폰트 등 정적 파일 |
| `components/` | 2개 이상 feature가 같이 쓰는 UI 컴포넌트만 |
| `config/` | 환경변수, 전역 상수 |
| `features/` | 실제 기능 로직. 대부분의 신규 코드는 여기 하위에 생김 |
| `hooks/` | 2개 이상 feature가 같이 쓰는 Hook만 |
| `lib/` | 외부 라이브러리를 초기화/래핑한 인스턴스 |
| `stores/` | 앱 전체가 공유하는 전역 상태만 |
| `types/` | 2개 이상 feature가 공유하는 타입만 |
| `utils/` | 외부 의존성 없는 순수 함수만 |

  사용합니다.


# 에러 처리 규칙

- 에러는 명확하게 처리합니다.
- 빈 catch 문을 사용하지 않습니다.
- 사용자에게 의미 있는 에러 메시지를 제공합니다.

피해야 할 예:

~~~ts
try {

} catch {}
~~~

권장:

~~~ts
try {

} catch (error) {
  console.error("Failed:", error);
}
~~~


# 리팩토링 규칙

리팩토링 시:

1. 기존 기능을 유지합니다.
2. 작은 단위로 변경합니다.
3. 관련 없는 파일은 수정하지 않습니다.
4. 구조 변경 시 이유를 설명합니다.


# Git 규칙

- 하나의 커밋은 하나의 목적만 가집니다.
- 관련 없는 변경을 섞지 않습니다.
- 기존 기능을 삭제하기 전에 확인합니다.


# AI 작업 규칙

AI는 다음을 지킵니다.

1. 코드를 수정하기 전에 기존 구현을 확인합니다.
2. 변경 이유를 설명합니다.
3. 새 파일 생성 시 전체 코드를 제공합니다.
4. 영향 범위를 알려줍니다.
5. 큰 구조 변경은 먼저 사용자에게 확인합니다.
6. 새 파일을 만들 때는 항상 "2개 이상 feature 공용인가, feature 전용인가"를
   먼저 판단하고 그에 맞는 위치(`src 구조 원칙` 섹션 참고)에 배치합니다. 새로운
   최상위 폴더를 임의로 만들지 않습니다.
7. 새로운 기능에 대한 구현 프롬프트나 개발 프로세스를 작성/수정할 때는
   `docs/content/` 폴더(Obsidian Vault)의 알맞은 주제별 폴더(`기획/`, `개발/` 등)에
   저장합니다. `docs/content/` 바로 아래에 파일을 흩어놓지 않고, `docs/` 최상위
   (Quartz 설정 위치)에는 절대 문서를 두지 않습니다.
8. 새 문서를 만들면 관련 태그(`#스펙`, `#체크리스트`, `#프롬프트` 등)를 달고,
   관련 허브 문서(`index.md` 등)에서 `[[..]]` 링크로 연결해 고립 문서가 생기지
   않도록 합니다.
